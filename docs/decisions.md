# 设计决策记录

格式：背景 → 决定 → 理由 → 代价。按 ADR 风格写，是为了让「为什么不那样做」也能被回答。

---

## D-001 权限隔离放在检索层，而不是 Prompt 层

**背景** 同一份知识库里有公开资料和受限资料，需要按用户档位控制可见范围。

**决定** 每个权限档位编译一套独立检索引擎：BM25 只索引该档可见语料，向量检索附加
Chroma `metadata` filter。受限 chunk 不进入 Prompt。

**理由** Prompt 里写「你不能透露 X」是在请求模型配合，攻击面包括越狱、指令改写、
以及模型自己把上文当常识复述。检索层过滤之后，越权内容**根本不在上下文里**，
模型无从生成 —— 这是能力边界，不是行为约束。

**代价** 每档一份 BM25 内存索引；档位数量影响启动和重建耗时。当前 2 档、55 chunk 无所谓。

## D-002 中文必须显式给 BM25 分词器

**背景** `BM25Retriever.from_documents` 默认 ` preprocess_func=str.split`。

**决定** 传入 `preprocess_func=jieba.lcut`。

**理由** 中文句子没有空格，默认分词等于把整句当成一个 token —— 词袋相似度对任何子串查询
都是 0，BM25 分支实际失效，混合检索退化成纯向量检索。这个 bug 不会报错，只会让
「加了 BM25」变成错觉。

**代价** 引入 jieba 依赖，首次加载词典约 0.6s。

## D-003 查询重写条件触发

**背景** 多轮对话需要把「它怎么配置」补全成独立查询，标准做法是每轮先调一次 LLM 重写。

**决定** 只在「有历史」且「问题命中中文指代词表」时才重写，否则用原问题直接检索。

**理由** 首轮请求占实际流量大头，为它们付一次额外 LLM 调用换不来任何召回提升。
重写延迟和成本都叠加在用户等待时间上。

**代价** 指代词表是启发式：漏词会导致该重写的没重写，召回下降；表外表达（如省略主语但无代词）
不会被覆盖。**这是本项目里我最没把握的一处**，正确解法是拿评测集量一遍，见 D-008。

## D-004 融合权重与 top-k 全部外置为环境变量

**背景** 0.5/0.5、top-20、top-3、chunk 800/20 这些数字一开始都是手调的。

**决定** 全部进 `Settings`，`requirements` 不改代码就能扫参。

**理由** 检索参数需要消融实验。硬编码的话，扫一遍参数 = 改一遍代码 = 无法交给别人复现。

**代价** 无。

## D-005 rerank 只做二次排序，不做全库打分

**决定** cross-encoder 的输入是融合后的 20 条候选，压到 3 条。

**理由** cross-encoder 每条候选都要和 query 拼起来跑一遍前向，全库打分是 `O(库大小)` 次
模型推理，规模上千后不可用。bi-encoder 可以预计算向量所以能扛全库。
候选 20 → 3 也顺带控制 Prompt 长度和幻觉面积。

**代价** 召回上限被第一段锁死：第一段没召回的，重排救不回来。

## D-006 阻塞计算下沉到线程

**决定** rerank/向量检索走 `asyncio.to_thread`，PDF 解析与索引重建走 `run_in_threadpool`。

**理由** sentence-transformers 和 pypdf 是同步库。直接在 `async def` 里调用会让整个
event loop 停摆 —— 单请求看不出问题，并发下 P99 会退化成串行总和。

**代价** torch 有 GIL/线程争用问题，设 `TOKENIZERS_PARALLELISM=false` 抑制 fork 告警。
CPU 上是可接受的；真高并发应改多进程或独立推理服务。

## D-007 上传文件名必须消毒

**背景** 原实现 `os.path.join(UPLOAD_DIR, file.filename)`，`filename` 完全由客户端控制。

**决定** `indexer.safe_filename()`：先 `Path(...).name` 去掉目录成分，再拒非 `.pdf`、
把控制字符与路径分隔符替换掉，最后断言结果父目录就是上传目录。

**理由** `../../x.pdf` 直接拼接可以写到容器/宿主机任意可写路径，是 OWASP 上的
Path Traversal。一个要公开的仓库里不该留着。

**代价** 同名文件互相覆盖 —— 没解决，见 Roadmap。

## D-008 删掉 `cache_hit` 字段

**背景** 原响应里 `cache_hit = latency < 0.1`。

**决定** 移除，改为返回 `level`。

**理由** 用耗时反推「是否命中缓存」不是测量，是猜测：慢网络会让真命中报成 false，
预热会让假命中报成 true。伪指标比没有指标更糟，因为它会喂给后续决策。

**代价** 少了一个好看的字段。真实做法是从 LangChain cache 拿命中事件再计数。

## D-009 单测只覆盖纯逻辑

**决定** `tests/` 只测 `config` / `text_cleaning` / `indexer`，不碰模型、Redis、HTTP。

**理由** 需要下载 1.2GB 权重和真实密钥的测试在 CI 里必然变成 flaky，然后被跳过，
最后失去价值。纯逻辑测试 0.4 秒跑完，能真正当回归网用。

**代价** 端到端链路没有自动化保护，靠 `/docs` 手动验证 + 待补的评测集。

## D-010 已知未解决：`user_level` 由客户端声明

**现状** `/chat` 直接信任请求体里的档位。

**为什么先这样** 这个项目的目的是验证「分级检索链路可行且可复现」，鉴权是另一条独立能力线。
把两者混在一起做，会让「检索设计是否有效」这个结论更难隔离出来。

**为什么这是限制而不是特性** 它只证明了数据侧能隔离，没证明系统能抵抗越权。
对外之前必须补：签发角色化 Token，服务端解析角色，请求体的 `user_level` 降级为
「请求」，以 Token 为准并 deny-by-default。
