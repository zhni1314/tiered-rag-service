# ADR-0013 放弃 PDF 混合表格解析（不移植 C 方案）

状态：已决定，2026-11-02
关联：接续 `docs/decisions.md` 的 D-012；本文件起改用 `docs/adr/` 单文件编号，避免与未提交的 D-012 混在同一次提交里。

## 决策

不做 `pdfplumber` 混合表格解析。具体地：

- 不把「pypdf 提正文 + pdfplumber 认表格转 Markdown」的解析路径移进 `src/`；
- 不引入 `pdfplumber` 依赖，`requirements.txt`、CI 的 `pip install`、Docker 镜像均不改动；
- 表格类文档继续走 `extract_pdf_pages()` 的单一正文路径，表格以纯文本形式入库；
- `legacy/app11-01.py` 里的实验实现保留为本地快照，标注「超出 `src/` 能力范围」，不再迭代。

## 背景

前一份 ADR（D-011）之后，父子分块已经上线，但评测语料里**没有任何带表格的文档**，
于是先造了 4 份含真实 `<table>` 标记的语料（3 份自编、1 份公开一手摘录），
围绕「表格解析」连续验证了四轮，最后一轮走出合成语料、用公开的真实 PDF 做外部验证。

## 实测数据

样本量先说清楚：合成语料 4 份 / 13 张表；真实文档 2 份（arXiv 论文，15 页与 26 页）。
其中「假合并」「双行表头」「合并单元格」各只有 **1 个正例或 1 个反例**，这是后面所有结论的天花板。

### 四轮里被证明成立的部分

| 项目 | 结果 |
|---|---|
| 双栏正文被 `outside_bbox` 切碎（v1 缺陷） | v1 整句保留 **0/9**，v2 **1/10**；改回「正文只用 pypdf」后 **10/10** |
| 表格行完整性 | pypdf 与 Markdown 表格两方案**同为** 20/20、47/47、26/26（难版式两边都 9/12）→ 表格化没有带来收益 |
| 切块长度 | 表格文档子块超 200 的数量 = **0**，靠的是 D-011 之后补的分隔符 `\n`，与解析器无关 |
| 跨页大表合并 | 36 行表跨页（24+14）合成 1 张、单元格保留 100%（n=1 正例） |
| 假合并拦截 | 两张同为 3 列、表头不同的表不再被焊死（n=1 反例） |
| 合并单元格归属 | 组名从 `rowspan` 展开到每行后 **3/8 → 7/7**（数据行真实为 7 行，第 8 行是表头） |
| span 几何推导 | 网格吸附法推出 rowspan=4 / colspan=2，与作者写在 HTML 里的意图**差值 0**（13 张表逐张核对）；反向测试：高行表用「比例法」误判 6 个 rowspan，吸附法为 0 |

### 被真实文档否掉的部分

| 检查 | 真实文档结果 |
|---|---|
| 表格召回 | RAG 综述（26 页）文中有 **6 张带标题的表**，`pdfplumber` 默认策略检出 **0 张**（booktabs 只有横线，无竖线） |
| 表格误检 | Attention 论文实际约 **4 张**表，默认策略检出 **10 张**；换 `vertical_strategy="text"` 变 15 张 / 749 行，等于把整页正文当表 |
| 正文质量 | 同一页 pdfplumber 只抽出 **37 字符**且单词粘连（`Table1:ComparisonbetweenRAG…`），pypdf 正常 |
| 载体对比 | HTML 载体下 **92/92 个子块超过 200 字符**（`<thead>` 前缀本身吃满预算），子块总字符是 Markdown 的 **4.5 倍**，一次回答能带的行数从 11 掉到 5（覆盖率 50%） |
| 代价 | 解析+切块耗时 **×3.0–4.4**（表格文档），**无表格文档也要 ×3.8**（`pdfplumber` 每页都得开）；第四轮加上吸附与展开后到 ×5.2–9.2 |

一句话：**合成语料全绿，真实文档全废。** 合成语料的表格都有框线，而真实技术文档的表格恰恰没有——收益建立在版式巧合上。

## 代价与纪律

不移植省下的是：一个永久依赖（`pdfplumber` + pdfminer.six + Pillow，Docker 镜像变大）、
上传路径 ×3–9 的耗时、三条只在 n=1 上验证过的启发式（合并三道条件、表头前缀判定、网格吸附）。
按本项目的纪律「每个功能带 1 个测试 + 1 个数字，且要经得起 20 分钟追问」，
一个「在我的合成语料上完美、在真实 PDF 上召回为 0」的能力，反而是负资产。

## 未测场景（以及为什么不再测）

A 股年报、政府公文、扫描件、无框线中文表格等版式一律未测。**不再补测**：
学术论文已经证伪了默认策略的召回，配置旋钮又被证明只是在「漏检」和「误检整页」之间换。
再堆语料只是给一个不成立的前提增加样本。

## 重选条件

满足全部三条才重新评估表格解析：

1. 有明确的用户文档场景报「表读不出来」，且该文档的表格**有可检测的框线或可判定的行列网格**；
2. 出现一个在 ≥2 份真实文档上召回不为 0 的检测配置（不是 `text+text` 这种把正文当表的配置）；
3. 表格能力带来的命中提升能在评测集上量出来（需要先把表格题纳入评测集，见 README Roadmap）。

## 本轮顺带的产出（已落地，与本决策无关但同源）

同一批真实文档暴露了 `extract_pdf_pages()` 之前的缺陷：**一份 26 页的 arXiv PDF 让 pypdf 在第 1 页抛
`AssertionError`，而旧实现没有任何异常保护，整个 `/upload` 直接 500**。
本轮改为逐页 try/except + 计数：修复后同一份文档正常入库（65,043 字，`pages_failed=1`，`failed_pages=[1]`），
干净文档 `pages_failed=0` 无回归。这条修复随本 ADR 一起提交。

## 复现说明

表格实验的语料与原型脚本都不进仓库：语料留在本地 `data/table_corpus/`（`.gitignore` 已覆盖 `data/`），
原型脚本在临时目录，第四轮的三列对比与逐表 span 差值报告已随本文归档数据。
真实验证用的两份 arXiv PDF 留在 `data/real_pdfs/`，因版权与来源原因**不得提交、不得并入 `examples/`**。
